# 一卡通系统故障复盘

## 故障 1：充值后余额不同步（高频，累计 20+ 次）

| 项 | 内容 |
|---|---|
| 发生时间 | 2025-09 ~ 2026-03，累计 20+ 次 |
| 影响范围 | 每次 1-15 名学生 |
| 严重程度 | 中（影响单个学生，但投诉率高） |
| 处理耗时 | 平均 30 分钟/次 |

### 现象

学生通过微信/支付宝充值，支付渠道显示扣款成功，但一卡通余额未增加。
食堂刷卡提示"余额不足"，学生需要到服务台处理。

### 排查过程

1. **查交易流水**
   ```sql
   SELECT * FROM transaction
   WHERE card_no='xxx' AND tx_type='RECHARGE'
   ORDER BY tx_time DESC LIMIT 3;
   ```
   发现记录存在，但 `status='PENDING'`。

2. **查网关日志**
   ```bash
   grep "callback" /var/log/gateway/gateway.log | grep xxx
   ```
   发现回调请求返回 **502 Bad Gateway**。

3. **查应用日志**
   ```bash
   grep "502" /var/log/tomcat/catalina.out | grep 时间点
   ```
   发现那个时间点应用正在重启（版本更新）。

4. **定位根因**
   - 网关回调超时设置为 3 秒
   - 应用重启需要 20-30 秒
   - 重启期间的回调全部超时失败
   - **且没有重试机制**，失败后消息直接丢弃

### 根因

**回调机制设计缺陷**：超时太短 + 无重试 + 无补偿。

### 解决方案

| 措施 | 具体做法 | 效果 |
|---|---|---|
| 1. 延长超时 | 回调超时 3s → 10s | 覆盖大部分重启场景 |
| 2. 增加重试 | 失败后重试 5 次，间隔 1/2/4/8/16 秒 | 覆盖短暂故障 |
| 3. 补偿任务 | 每天扫描 `PENDING` > 10 分钟的记录，自动补单 | 兜底 |
| 4. 灰度发布 | 应用重启改为滚动发布，避免全部实例同时下线 | 减少影响面 |

### 效果

同类故障从**每周 2-3 次降到 0**（2026-04 至今未再发生）。

### 教训

**异步系统必须考虑失败场景。** 回调不是 100% 成功的，必须有重试和补偿。

## 故障 2：消费流水丢失（1 次，影响 47 笔）

| 项 | 内容 |
|---|---|
| 发生时间 | 2025-11-08 |
| 影响范围 | 47 笔消费，涉及 23 名学生，金额 1,240 元 |
| 严重程度 | 高（资金对不上） |
| 处理耗时 | 6 小时 |

### 现象

月末对账时发现，某些 POS 机的消费记录在中心库缺失，但学生确实消费了。

### 排查过程

1. **对比数据**
   ```sql
   -- 中心库流水
   SELECT COUNT(*) FROM transaction
   WHERE pos_id='P05' AND DATE(tx_time)='2025-11-08';
   -- 结果: 128

   -- POS 机本地日志（导出后统计）
   -- 结果: 175
   ```
   差 47 笔。

2. **查 POS 机通信日志**
   发现当天 14:20-15:10 有网络中断记录。

3. **查 POS 机上传逻辑**
   查看厂商提供的文档和日志，发现：
   - 网络中断时数据缓存在本地
   - 恢复后批量上传
   - **上传失败的数据直接丢弃**（代码逻辑 bug）

### 根因

**POS 机固件 bug**：上传失败无重试，直接丢弃。

### 解决方案

| 措施 | 具体做法 |
|---|---|
| 1. 厂商修复 | 反馈厂商，升级 POS 机固件（改为失败重试 + 本地保留 7 天） |
| 2. 人工补录 | 从 POS 机本地导出缺失的 47 笔，手工补录 |
| 3. 增加校验 | 对账脚本增加「POS 机流水数 vs 中心库流水数」比对 |
| 4. 网络冗余 | POS 机增加 4G 备用网络 |

### 效果

- 47 笔已全部补录，金额核对无误
- 固件升级后未再发生
- 对账脚本现在能提前发现这类问题

### 教训

**不要完全信任终端设备。** 中心系统要有兜底校验。

## 故障 3：主从延迟导致查询到旧数据（多次）

| 项 | 内容 |
|---|---|
| 发生时间 | 新生入学、学期初集中出现 |
| 影响范围 | 查询页面显示旧数据 |
| 严重程度 | 中（数据没错，只是显示延迟） |
| 处理耗时 | 30 分钟 - 2 小时 |

### 现象

学生刚充值，查询页面显示的仍是旧余额。刷新几次后才正常。

### 排查过程

1. **查主从状态**
   ```sql
   SHOW SLAVE STATUS\G
   -- Seconds_Behind_Master: 120
   ```
   延迟 120 秒。

2. **查主库正在执行的事务**
   ```sql
   SELECT * FROM information_schema.innodb_trx
   WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60;
   ```
   发现一个批量导入新生数据的事务，50 万行。

3. **定位根因**
   - 批量导入在**一个事务**里
   - 从库**单线程**回放
   - 主库执行 3 秒，从库回放要几分钟

### 根因

**大事务 + 单线程回放**。

### 解决方案

| 措施 | 具体做法 | 效果 |
|---|---|---|
| 1. 分批提交 | 批量导入每 5000 行提交一次 | 从库能追上 |
| 2. 并行回放 | `slave_parallel_workers=4` | 回放速度 ×3 |
| 3. 关键查询走主库 | 余额查询强制主库 | 用户无感知 |
| 4. 增加监控 | 延迟 > 10 秒告警 | 提前发现 |

### 效果

- 延迟从 120 秒降到 5 秒以内
- 批量导入期间用户无感知

### 教训

**主从架构要区分读写场景。** 强一致性要求的查询必须走主库。

## 总结：三个故障的共同点

| 故障 | 表面原因 | 根本原因 |
|---|---|---|
| 1. 充值不同步 | 回调失败 | 异步设计缺少重试与补偿 |
| 2. 流水丢失 | POS 上传失败 | 终端设备不可信，缺少兜底校验 |
| 3. 主从延迟 | 大事务 | 未区分读写场景，缺少监控 |

**共同点：都是"设计时没考虑到失败"导致的。**

系统设计时容易只考虑"正常流程"，但生产环境的故障大多来自异常分支。
现在做任何改动，我都会先问一句：**"如果这一步失败了，会怎样？"**
