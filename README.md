# 校园一卡通系统运维与故障处理

一卡通系统日常巡检、故障排查、自动对账的运维实践记录。

## 背景

在学校信息中心勤工助学，负责一卡通系统运维，累计处理 40 余起报障。
一卡通涉及充值、消费、门禁、图书借阅，一旦出问题影响面很大（食堂刷不了卡 = 全校学生吃不上饭）。

这份仓库把日常运维的经验整理成可复用的脚本和文档。

## 系统架构

```
        学生/教职工
             │
    ┌────────┴────────┐
    │                 │
 消费POS机         充值终端
    │                 │
    └────────┬────────┘
             │  专网
        ┌────▼─────┐
        │ 交易网关  │  ← 异步处理，回调通知
        └────┬─────┘
             │
    ┌────────┴─────────┐
    │                  │
┌───▼────┐      ┌──────▼──────┐
│ 应用服务 │      │  MySQL 主库  │
│ (3 台)  │─────>│  + 从库      │
└────────┘      └─────────────┘
```

关键点：**交易网关是异步的**，充值/消费请求先落队列，再回调通知应用层更新余额。这个异步设计是很多故障的根源。

## 日常巡检

```bash
# 每天 8:00 定时执行
./scripts/daily_check.sh
```

巡检项：

| 类别 | 检查内容 | 告警阈值 |
|---|---|---|
| 系统 | CPU / 内存 / 磁盘 / 负载 | CPU>80%、磁盘>85% |
| 数据库 | 主从延迟、连接数、慢查询 | 延迟>10s、连接>200 |
| 应用 | 进程存活、端口监听、JVM 堆 | 进程挂掉即告警 |
| 业务 | 当日交易量、失败率 | 失败率>1% |
| 对账 | 交易流水与余额差异 | 有差异即告警 |

## 自动对账

python scripts/reconcile.py --date 2026-06-15
```

      │                                │
      └──────────┬─────────────────────┘
                 │
        按 (卡号, 日期) 汇总
                 │
          比对金额与笔数
                 │
        ┌────────┴────────┐
        │                 │
      一致              不一致
        │                 │
      记录正常        生成差异工单
```

## 关键故障复盘

### 故障 1：充值后余额不同步（最高频）

**现象**：学生充值成功，钱扣了，但余额没加。食堂刷卡提示余额不足。

**排查过程**：

1. 查交易流水表，发现充值记录存在，状态是 `PENDING`
2. 查网关日志，发现回调请求返回 502
3. 查应用日志，502 是因为回调时应用正在重启
4. **根因**：回调超时设置太短（3 秒），应用重启期间的回调全部失败，且没有重试机制

**解决**：
1. 回调超时从 3 秒改为 10 秒
2. 增加失败重试（最多 5 次，间隔递增）
3. 增加补偿任务：每天扫描 `PENDING` 状态的充值记录，超过 10 分钟的自动补单

**效果**：同类故障从每周 2-3 次降到 0。

### 故障 2：消费流水丢失

**现象**：月末对账时发现，某些 POS 机的消费记录在流水表里缺失，但学生确实消费了。

**排查过程**：

1. 对比 POS 机本地日志和中心库流水，缺失 47 笔
2. 检查 POS 机与网关的通信日志，发现网络中断时段
3. **根因**：POS 机离线时数据缓存在本地，网络恢复后批量上传，但上传时如果有失败就丢弃了（代码逻辑 bug）

**解决**：
1. 反馈给厂商修复上传逻辑（改为失败重试）
2. 增加本地兜底：POS 机本地保留 7 天数据，可人工导出
3. 对账脚本增加「POS 机流水数 vs 中心库流水数」比对

### 故障 3：主从延迟导致查询到旧数据

**现象**：学生刚充值，查询页面显示的还是旧余额。

**排查过程**：

1. 查 `SHOW SLAVE STATUS`，`Seconds_Behind_Master` 达到 120 秒
2. 检查主库，发现有个大事务（批量导入新生数据，50 万行）
3. **根因**：批量导入在一个事务里，从库单线程回放，追不上

**解决**：
1. 批量导入改成分批提交（每批 5000 行）
2. 从库开启 `slave_parallel_workers=4`
3. 关键查询（余额）强制走主库

## 踩过的坑

1. **巡检脚本把磁盘告警阈值设成 95%，结果磁盘满了才告警**
   一卡通日志增长很快，95% 时只剩几小时余量。
   解决：改到 85% 告警，并加上「按增长速度预测何时满」的计算。

2. **对账脚本按「卡号+日期」分组，跨零点的交易对不上**
   23:59:59 的消费和 00:00:01 的回调，分属两天。
   解决：按「交易时间」而非「回调时间」分组，并允许跨天容差（前后各 1 小时）。

3. **日志切割后正在写的日志丢失**
   用 `mv` 切割，Tomcat 还持有原文件句柄，继续写到已被 mv 的文件里。
   解决：改用 `copytruncate` 方式，或者重启应用。

4. **慢查询日志把磁盘写满了**
   开了慢查询日志但没设上限，一个月写了 80GB。
   解决：`long_query_time` 从 0.1 调到 1，并加 logrotate。

5. **Zabbix 告警风暴**
   一次网络抖动，200 多个监控项同时告警，手机被短信轰炸。
   解决：加告警聚合（相同类型 5 分钟内只发一次）和依赖关系（网络故障时抑制应用告警）。
